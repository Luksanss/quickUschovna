# quickUschovna: the Finder Quick Action

In Finder, select files and folders, right-click, and choose **Quick Actions › Send with Úschovna**.
The selection goes to the app as one package, the same as a drop on the menu-bar icon. The
extension shows nothing itself, and Launch Services starts the app if it isn't running.

Researched and built on 2026-10-04 on macOS 27.0.1 with Xcode 27.0. Anything marked **(verified)**
was run on that Mac (details in § How it was verified). Nothing was clicked in Finder's real menu,
because the agent had no Accessibility permission. That last step is the manual test below.

## How it works

```
Finder: Quick Actions › Send with Úschovna
  │  AppKit builds one NSExtensionItem, with one attachment per selected file or folder
  ▼
QuickAction.appex (sandboxed, no UI): ActionRequestHandler
  │  each attachment → its file URL
  │  NSWorkspace.open(urls, withApplicationAt: the app that contains it,
  │                   activates: false, addsToRecentItems: false)
  ▼
Launch Services: launches quickUschovna.app if needed, then sends one "open documents" event
  │  with every URL, plus read access to each item
  ▼
AppDelegate.application(_:open:)  (quickUschovna/App/QuickActionReceiver.swift)
  │  one main-queue turn later, after launch has finished
  ▼
AppModel.send(urls): one package
```

| File | Job |
|---|---|
| `QuickAction/ActionRequestHandler.swift` | The extension: resolves each attachment to a URL and opens them all, at once, with its containing app. |
| `QuickAction/Info.plist` | Puts the extension in Finder's Quick Actions; the keys are below. |
| `QuickAction/Assets.xcassets` | The menu icon, generated by `scripts/make-quick-action-icon.swift`. |
| `quickUschovna/App/QuickActionReceiver.swift` | The app side: `application(_:open:)` → `model.send`. |
| `quickUschovna/Info.plist` | `CFBundleDocumentTypes`, without which the extension can't open anything with the app. |

The extension finds the app by its own path (`quickUschovna.app/Contents/PlugIns/QuickAction.appex`),
so it always hands over to the copy it ships in, never to some other copy with the same bundle ID.

## Why this mechanism

- **An Action extension is the only way into the Quick Actions submenu (verified).** AppKit's
  Finder presentation (`_NSQuickActionPresentation`, mode `Finder`) lists extensions whose point is
  `com.apple.services` or `com.apple.ui-services` and which set
  `NSExtensionServiceAllowsFinderPreviewItem`. Their title comes from
  `NSExtensionServiceFinderPreviewLabel` and their icon from `NSExtensionServiceFinderPreviewIconName`.
  `NSServices` entries in the app's Info.plist go to the Services submenu instead. A Finder Sync
  extension is meant for sync badges in watched folders.
- **`com.apple.services` with an `NSExtensionRequestHandling` principal class** is Xcode's "Action
  Extension › No User Interface" template. There's no view controller, so nothing can flash on
  screen. The `com.apple.ui-services` variant would need an `NSViewController`.
- **Role `NSExtensionServiceRoleTypeViewer`.** Apple's App Extension Programming Guide says an
  editor works on one item at a time, while a viewer can take several. An editor also returns edited
  items for the host to put in place of the originals: SAP's open-source icon generator warns that
  an editor which leaves an input out of its output gets that input deleted. A send action must
  never risk that. A viewer changes nothing.
- **Hand-off through Launch Services** (`NSWorkspace.open(_:withApplicationAt:configuration:)`):
  - it launches the app if it isn't running (verified);
  - every selected item arrives in **one** `application(_:open:)` call, so they make one package,
    and folders arrive as folders (verified);
  - **the app can read the items in Desktop, Documents and Downloads without a privacy prompt
    (verified)**. Launch Services passes the extension's access to each item on to the app, like a
    double-click in Finder does. A custom URL scheme that carried paths would leave the app (not
    sandboxed) facing a "would like to access files in your Documents folder" prompt instead.
- **The app must declare document types for this.** A sandboxed caller gets
  `kLSAppDoesNotClaimTypeErr` (-10820, "sandboxed callers only") when it opens a file with an app
  that doesn't claim that type (verified). So `quickUschovna/Info.plist` claims `public.item`, which
  covers every file, folder and package, with `LSHandlerRank` `None`. With rank `None` the app is
  never a default opener and doesn't appear in Finder's Open With menu (verified for a text file,
  a JPEG and a folder), yet the open from the extension is accepted.

## Info.plist keys

`QuickAction/Info.plist`, merged with the keys Xcode generates:

| Key | Value | Why |
|---|---|---|
| `CFBundleDisplayName` | `Send with Úschovna` | The name `pluginkit` and System Settings show. |
| `NSExtensionPointIdentifier` | `com.apple.services` | A headless Action extension. |
| `NSExtensionPrincipalClass` | `$(PRODUCT_MODULE_NAME).ActionRequestHandler` | An `NSExtensionRequestHandling` object, not a view controller. |
| `NSExtensionServiceAllowsFinderPreviewItem` | `true` | Lists it in Finder's Quick Actions (context menu and Preview pane). |
| `NSExtensionServiceFinderPreviewLabel` | `Send with Úschovna` | The menu item's title. |
| `NSExtensionServiceFinderPreviewIconName` | `QuickActionIcon` | An image set in the extension's asset catalog (§ The icon). |
| `NSExtensionServiceRoleType` | `NSExtensionServiceRoleTypeViewer` | Several items at once, originals untouched. |
| `NSExtensionActivationRule` | the predicate below | Any selection of one or more files or folders. |

```
SUBQUERY (
    extensionItems, $extensionItem,
    SUBQUERY (
        $extensionItem.attachments, $attachment,
        ANY $attachment.registeredTypeIdentifiers UTI-CONFORMS-TO "public.item"
    ).@count >= 1
).@count >= 1
```

Each attachment AppKit builds for a Finder selection registers the item's own type plus
`public.file-url` and `public.url` (verified). A folder without an extension gets a dynamic type such
as `dyn.age8u`, so the rule has to rely on `public.item`, which every file and folder type conforms
to, rather than on `public.data` or a list of types. The rule replaces the template's
`TRUEPREDICATE` and its build warning.

The extension's entitlements are the template's and were not changed: `com.apple.security.app-sandbox`
and `com.apple.security.files.user-selected.read-only`, from the `QuickAction` target's
`ENABLE_APP_SANDBOX` and `ENABLE_USER_SELECTED_FILES` build settings. The project file is not
changed: the target's folder is a synchronized group, so the asset catalog is picked up on its own.

`quickUschovna/Info.plist`: `CFBundleDocumentTypes` with one type, `Files and Folders to Send`:
`LSItemContentTypes` `public.item`, `CFBundleTypeRole` `Viewer`, `LSHandlerRank` `None`.

## The icon

The menu-bar icon's idle glyph (`design/prototype/MenuBarIcon.dc.html`, `isIdle`), 15 pt wide in a
16 pt image, as in the prototype's context menu. `scripts/make-quick-action-icon.swift` draws it
from the SVG's paths, so the binaries can always be rebuilt. Run it from the repository root after
changing the glyph:

```sh
swift scripts/make-quick-action-icon.swift
```

It writes `QuickAction/Assets.xcassets/QuickActionIcon.imageset`: 16 × 16 and 32 × 32 PNGs, in
black for the light appearance and white for the dark one, each at 85 % opacity like the system
label colour. It is **not** a template image, although Apple's documentation for the icon key asks
for one:

- AppKit hands Finder the icon as IconServices image reps (`NSISIconImageRep`), which lose the
  template flag. A template version of this glyph came back with `isTemplate == false` and drew
  black on the dark background (verified). Developers report the same on the Apple Developer Forums
  (thread 788162).
- An image set with a dark appearance variant draws black in light mode and white in dark mode
  through that same path (verified, rendered with `_NSExtensionQuickAction`'s icon loader).
- Bitmaps of exactly 16 pt: the same forum thread reports that larger images are cropped, not scaled,
  and that SVGs come out at the wrong size.

Not verified: how Finder draws the icon on the highlighted row. A template icon would turn white
there; this one keeps its appearance's colour.

## Turning it on

**A Quick Action is off until the user turns it on (verified).** AppKit treats an extension that
has no entry in the `pbs` defaults domain's `FinderActive` dictionary as inactive, because
`NSQuickActionsAreActiveByDefault` isn't set. Once installed, the action is listed but unticked. To
turn it on once:

1. In Finder, right-click any file, then choose **Quick Actions › Customize…**. That opens System
   Settings' list of Finder extensions, which lives under **General › Login Items & Extensions**,
   Extensions. The exact labels on macOS 27 weren't checked.
2. Tick **Send with Úschovna**.

This writes `"APPEXTENSION-com.luksanss.quickUschovna.QuickAction" = 1` into `FinderActive`, and it
lasts across rebuilds and updates because it's keyed by the extension's bundle ID. No
`pluginkit -e use` is needed: PlugInKit's default election already allows it. The app could
point users there on first run (for example a line in the first-run bubble); that's a design decision.

## Testing by hand

1. Build: `xcodebuild -project quickUschovna.xcodeproj -scheme quickUschovna -configuration Debug
   -derivedDataPath build/DerivedData.noindex build`. Xcode registers the built app with Launch
   Services, and its extension with PlugInKit, as part of the build.
2. Check that the system sees the right copy:
   `pluginkit -mAvvv -i com.luksanss.quickUschovna.QuickAction`. The `Path` should be the build you
   just made, the SDK `com.apple.services`, the display name `Send with Úschovna`. If several copies
   exist (other worktrees, `/Applications`, an old DerivedData), PlugInKit picks one of them; see
   § Re-registering.
3. Turn it on once (§ Turning it on).
4. Watch the log in Terminal:
   `log stream --level debug --predicate 'subsystem == "com.luksanss.quickUschovna" AND category == "quickAction"'`
5. Quit quickUschovna. In Finder, select two files and a folder on the Desktop, right-click, and
   choose **Quick Actions › Send with Úschovna**. Expect: nothing flashes, the app starts, and the
   log shows `Handed 3 item(s) to the app` from `QuickAction`, then `Received 3 of 3 item(s) to send`
   from `quickUschovna`. No privacy prompt appears.
6. With the app running, do it again with one file: one more `Received 1 of 1 item(s) to send`, and
   no second copy of the app in Activity Monitor.
7. Check the icon in the menu in light and dark mode, and that Open With on a file doesn't list
   quickUschovna.

### Re-registering

Building re-registers on its own. If Finder still shows an old title or icon, or the action
disappears:

```sh
LSREGISTER=/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister
$LSREGISTER -f build/DerivedData.noindex/Build/Products/Debug/quickUschovna.app
pluginkit -a build/DerivedData.noindex/Build/Products/Debug/quickUschovna.app/Contents/PlugIns/QuickAction.appex
```

Then relaunch Finder (Option-right-click its Dock icon › Relaunch). To drop a stale copy, for
example a deleted worktree's build: `$LSREGISTER -u <that app>` and `pluginkit -r <that appex>`.

## Known limitations

- **Off until ticked once** (§ Turning it on).
- **Read access lasts as long as the app runs.** Launch Services grants it to the running process.
  If the app ever keeps a queue across a relaunch, it will need another way back into
  Desktop, Documents and Downloads for those items.
- **Anything that opens files with the app sends them**, e.g. `open -a quickUschovna file`. That's
  `application(_:open:)` working as intended.
- **The menu click itself was not tested** (no Accessibility permission for the agent). Verified
  instead, through the AppKit API that Finder's menu is built on: the action is listed for Finder,
  it's valid for a lone folder, for a mix of files and a folder, and for a package, and not for an
  empty selection; invoking it delivers the items. The manual test above covers the click.
- **The icon on a highlighted row** may stay dark in light mode (§ The icon).
- **Copies with the same bundle ID compete.** During development, every worktree's build registers
  `com.luksanss.quickUschovna.QuickAction`, and PlugInKit uses one of them. It may not be the one
  you just built (seen while building this).

## How it was verified

On 2026-10-04, with throwaway tools (not in the repo). To keep the other worktrees' builds out of
the way, the Release build was copied to a scratch folder under unique bundle IDs
(`com.luksanss.quickUschovna.qatest`, `….qatest.QuickAction`), then re-signed with the same Apple
Development identity and entitlements and registered. Everything was unregistered and deleted
afterwards.

- **Through AppKit's Quick Action API**, the code Finder's menu is built on: `_NSQuickActionProvider`
  for the Finder mode listed the action as inactive until its `FinderActive` entry was set, then
  as active. That entry was then removed again, leaving `FinderActive` as it was.
  `_NSExtensionQuickActionValidation` judged it valid for the selections listed above.
  `_NSExtensionQuickAction performWithItemSource:`, given an item source whose `selectionItems`
  are file URLs, ran the extension: the app launched and got 3 items in one call.
- **Through `NSExtension` directly** (as a host app would), with three ways of building attachments:
  a URL object, a file opened in place, and the legacy type-plus-URL item. All delivered.
- **Privacy:** items in `~/Documents` were sent to the test copy, which had never been granted
  Documents access. The app read a file, listed the folder, and read a file inside it, with no
  prompt. `tccd` logged no `kTCCServiceSystemPolicyDocumentsFolder` request for it.
- **Launch order:** on a cold launch, `application(_:open:)` runs before
  `applicationDidFinishLaunching(_:)`, and a block queued on the main queue from it runs after. Hence
  the one-turn delay in `QuickActionReceiver.swift`.
